## 發現與建議

### P1／高：0 候選結果仍容易被逐藥文字誤讀成推薦

**重現步驟**

1. 在病例工作台選擇 `agent-complete · revision 3`。
2. 在執行紀錄開啟 `91ddb348`。
3. 由分析結果或證據與流程查看「逐藥決策表」。
4. 先由左至右掃讀 amoxicillin_clavulanate、amikacin、aztreonam 等列，再讀最右側欄。

**畫面原文**

- 頂端：`Agent 主導判斷 · 18 項藥品 · 0 項可供審閱 · 18 項待確認`
- 頂端安全提示：`目前沒有完成核對的可供審閱選項。請分別查看待確認與不建議的理由；此結果不等於所有藥品均不適用。`
- amoxicillin_clavulanate：`敏感`、`適合用於治療本患者的下泌尿道感染`、`有支持`、`適合使用`
- amikacin：`使用amikacin治療具良好療效`、`有支持`
- 臨床風險欄：`未完成`，且 `過敏：未核對`、`腎功能：未核對`、`交互作用：未核對`
- 最終欄：`待確認`、`臨床風險未解決`

**醫師可能如何誤解**

醫師在長表中常先看藥名、藥敏與摘要句。若看到「敏感」「有支持」「適合使用」，可能先形成可用藥印象，而沒有水平捲動或讀到末欄的失敗狀態。頂端總結雖正確，但不能抵銷每列反覆出現的肯定語氣。

**建議**

- 每列最左側緊鄰藥名先顯示醒目的 `不可供審閱：臨床風險 Agent 失敗`。
- 把「最終去向」移到藥名後的第二欄，讓狀態先於模型理由。
- 當任何必要 Agent 失敗時，把肯定語句包在 `模型原文（未驗證，不可作為推薦）` 區塊，摘要改成中性敘述，例如 `模型聲稱有支持；尚未通過必要檢核`。
- `有支持` 應拆成 `Evidence Agent 聲稱支持` 與 `整體檢核狀態`，避免被理解成系統結論。

### P1／高：ertapenem 的模型理由與同頁來源資料直接矛盾

**重現步驟**

1. 在病例工作台的來源 AST 找到 ertapenem。
2. 開啟 `91ddb348`，在逐藥表或「06 引用獨立複核」找到 ertapenem。

**畫面原文**

- 病例來源 AST：`原始測量 <= 0.5 broth_microdilution · 原檔未提供單位`、`原始報告 Susceptible`、`CLSI 2022 衍生判讀 未提供`
- 逐藥表：`MIC：未提供（不自行換算）`
- 引用獨立複核：`雖CLSI未明確報告敏感性，但MIC值低且無抗藥性紀錄，推測菌株對ertapenem敏感。`

**醫師可能如何誤解**

後一句會被理解成系統已讀到可靠 MIC 並做出低值判讀，但同頁明確說原檔未提供單位、MIC 未提供、不可自行換算。這會讓來源可追溯性失去可信度。

**建議**

- 增加跨欄一致性檢查：只要來源欄為 `MIC 未提供`，任何 Agent 文本出現 `MIC 值低／高` 就標示 `與來源資料矛盾`，並禁止進入「有支持」。
- 在理由旁直接並列來源事實：`CLSI：未提供；MIC：未提供；原始報告：Susceptible`。
- 將此類矛盾列入「需確認事項」，不要只保留在長篇模型原文中。

### P1／高：臨床 Agent 失敗，但已存在的病例資料看起來像完全沒被看過

**重現步驟**

1. 在病例摘要查看過敏、腎功能與用藥資料。
2. 在逐藥表查看任一藥品的臨床風險欄。
3. 到證據與流程展開 `04 臨床風險 Agent · 執行失敗`。

**畫面原文**

- 病例：`已記錄無已知過敏。病歷標籤與是否確認分別保留。`
- 病例：`用藥紀錄核對：已確認目前無用藥。`
- 病例：`CrCl：84.1 mL/min`，另有 `eGFR 92 mL/min/1.73m2`
- 每個藥品：`過敏：未核對`、`腎功能：未核對`、`交互作用：未核對`
- Agent 展開：`此步驟沒有可用回覆；其他已完成步驟仍可查看。`、`回覆未通過格式或來源檢核，未完成評估。`

**醫師可能如何誤解**

`未核對` 可能被理解成病例缺資料或尚未有人輸入，而真正原因是模型回覆不可用。這會讓醫師錯誤地回頭補填已有資料，或以為某些風險已由其他 Agent 代為處理。

**建議**

- 改成 `病例已有資料，但臨床風險 Agent 輸出無法使用；本項未評估`。
- 在 Agent 摘要列出「已提供輸入」與「未產生可用結論」，例如過敏標籤、用藥狀態、CrCl/eGFR。
- 若失敗原因是格式或來源檢核，顯示可行的下一步；不要只寫泛稱錯誤。

### P1／高：引用標題與主張明顯不相符時仍顯示「有支持」

**重現步驟**

1. 開啟逐藥表與 `06 引用獨立複核`。
2. 查看 meropenem、piperacillin_tazobactam、ampicillin 等列的理由與引用標題。

**畫面原文例子**

- meropenem：主張 `藥品說明書支持meropenem用於複雜感染包括尿路感染`，引用卻顯示 `8 USE IN SPECIFIC POPULATIONS / 8.5 Geriatric Use`；病例年齡為 45。
- piperacillin_tazobactam 在逐藥表可見引用標題 `Female Pelvic Infections`，病例情境是模擬 lower urinary tract infection。
- ampicillin：理由談下尿路感染與過敏，引用之一為 `PRECAUTIONS / Drug Interactions`。
- 同一畫面仍可能顯示 `有支持`、`感染：有支持；族群：有支持；藥品：有支持`。

**醫師可能如何誤解**

`有支持` 看起來像引用已證明該病例、感染部位與用藥主張相符。實際上，至少從標題即可看出部分片段不能支撐緊鄰的主張。醫師若未逐一展開原文，會高估證據品質。

**建議**

- 獨立複核未通過時，不顯示無限定詞的 `有支持`；改為 `模型判稱有支持，引用適用性未通過`。
- 引用標題與主張的感染部位、族群或段落類型不一致時，自動標成 `疑似不相符` 並排到列首。
- 應保留目前「0 候選」阻擋，不要用 UX 標示假裝已完成臨床適用性驗證。

### P2／中：Agent 自身說「未列出額外待確認事項」，與步驟狀態及整體結果不一致

**重現步驟**

1. 到證據與流程。
2. 展開 `03 證據 Agent · 需確認`。
3. 展開 `06 引用獨立複核 · 需確認`。

**畫面原文**

- 兩個 Agent 均顯示：`此步驟未列出額外待確認事項。`
- 但標題為 `需確認`，整體為 `18 項待確認`，且引用獨立複核內部分藥品標成 `待確認`。

**醫師可能如何誤解**

使用者無法判斷「需確認」究竟是 Agent 真的提出了問題、系統驗證失敗，還是單純的通用狀態。這也削弱了「展開 Agent 缺漏」的用途。

**建議**

- 把待確認來源分為 `Agent 提出的臨床問題`、`系統格式／來源檢核`、`引用適用性檢核`。
- 若 Agent 沒有自行列出問題，但系統檢核使其需確認，明寫 `Agent 未提出問題；系統另偵測到以下檢核缺口`。
- 在摘要列出受影響藥品與具體原因，不要只顯示重複的 evidence_context 長度警告。

### P2／中：逐藥證據準備表資訊完整，但技術警告與重複列淹沒臨床重點

**重現步驟**

1. 在結果頁展開 `逐藥證據準備與呼叫情況`。
2. 比較共同感染情境、共同指引選項與每個藥品的 Evidence／Clinical Risk Agent 列。

**畫面原文與觀察**

- 頂端說明清楚：`片段數表示輸入準備情況，不代表支持用藥、已送達模型或已完成核對。`
- 呼叫狀態也清楚：`已收到模型回覆；不代表核對通過`。
- 共同感染情境可見 `找到 23／準備 14／省略 9`，共同指引選項可見 `找到 11／準備 9／省略 2`。
- 每個藥品分別列 Evidence Agent 與 Clinical Risk Agent，並反覆顯示 `long_text_split`、`page_2_blank`、`page_310_blank`、`page_7_table_needs_review` 等技術字串。

**醫師可能如何誤解或受阻**

「已收到模型回覆」與 Agent 最後「執行失敗」要靠細讀才能拼起來：呼叫成功不代表輸出格式通過。大量重複列與英文 parser token 讓使用者很難快速找到哪個藥真的少了關鍵證據。

**建議**

- 預設只顯示失敗、省略或不一致列，提供藥品與 Agent 篩選。
- 將呼叫生命週期拆成 `送出／收到回覆／格式檢核／來源檢核／可用結論`。
- 把技術 token 收進「技術詳細資料」，外層翻譯成 `部分頁面空白`、`表格需人工檢查`、`長文已切段`，並合併重複警告。

### P2／中：文件庫的論文分類清楚，但直接露出技術 token，族群依據也未保存

**重現步驟**

1. 到文件資料庫。
2. 展開 `Characteristics, risk factors and clinical impact of penicillin and other antibiotic allergies in adults in the UK General Practice: A population-based cohort study`。

**畫面原文**

- `真實參考文件（適用性仍需核對）`
- `證據類型：研究文章（背景證據） · 研究設計：觀察性研究`
- `適用地區：UK`
- `目前族群標示與依據 成人`
- `未保存族群標示的變更紀錄或依據，請核對文件。`
- 未翻譯字串：`page_7_table_needs_review`
- `技術資料：文件索引與中繼資料（JSON）` 為折疊項目，沒有在一般畫面直接展開 JSON，這一點良好。

**醫師可能如何理解**

「研究文章（背景證據）」與「觀察性研究」足以和感染指引、藥品標示區分，分類是清楚的。但 `page_7_table_needs_review` 像系統錯誤碼，且「成人」沒有保存標示依據，會使使用者不確定這個族群標示能否信任。

**建議**

- 將 token 顯示為 `第 7 頁表格需人工檢查`，原 token 放入技術折疊。
- 族群為 `成人` 但沒有依據時，外層標成 `成人（依據未記錄，不能作為候選支持）`。
- 保留目前的研究類型、設計、地區與「背景證據」分類。

### P3／低至中：過敏資料欄位完整，但一個確認狀態用語不直觀

**重現步驟**

1. 到病例工作台。
2. 展開 `補充過敏紀錄（保存為新病例版本）`。
3. 按 `新增過敏紀錄`，只查看空白欄位，不保存。

**畫面原文**

- 提示：`保留原始標籤；填寫既有評估的來源，不由模型解除標籤。保存後需重新分析，舊結果不變。`
- 欄位：`藥品代碼`、`原始反應`、`嚴重程度`、`標籤來源`、`發生時間（可填約略日期）`、`確認狀態`、`既有評估內容`、`評估來源／紀錄位置`、`確認紀錄者`、`確認時間（含時區）`
- 確認狀態：`未提供確認狀態`、`尚未確認`、`已有確認紀錄`、`已有評估排除紀錄`、`紀錄互相矛盾`

**醫師可能如何誤解**

欄位整體足以區分原始標籤、反應、嚴重程度與後續評估，且明示模型不能解除標籤，設計方向良好。`已有評估排除紀錄` 可能被理解成「已排除某份紀錄」，不一定立即理解為過敏已經由既有評估排除。

**建議**

- 將選項改成 `已有臨床評估：不支持此過敏標籤`，並在選取後要求填寫評估來源、紀錄位置、確認者與時間。
- 在表單上方保留目前「保存為新病例版本／舊結果不變」提示。

### P3／低至中：同一本 WHO 內容看起來像兩個獨立來源

**重現步驟**

1. 查看逐藥理由與引用。
2. 注意同列內同時出現 `WHO AWaRe lower UTI chapter` 與 `who`。

**醫師可能如何誤解**

兩個名稱容易被計成兩份相互獨立的來源，實際畫面內容顯示它們都指向 WHO AWaRe 的相關頁面。

**建議**

- 顯示文件的共同作品／版本識別，並標示 `同一來源的不同匯入版本或節錄`。
- 證據數量統計應以獨立作品為單位，另列片段數，避免重複來源造成支持度膨脹的印象。

## 已做得清楚的安全設計

- 頂端明示 0 項可供審閱，並說明這不等於所有藥品均不適用。
- 臨床風險 Agent 展開明示 `執行失敗`，沒有把呼叫完成偽裝成評估完成。
- 逐藥證據準備區明示片段數不代表支持、送達或核對完成；呼叫狀態明示收到回覆不代表核對通過。
- 病例摘要清楚區分來源 AST、人工編製情境與模擬欄位；CrCl 也說明是以 authored values 計算，而非觀測值。
- 過敏表單保留原始標籤與確認紀錄，不允許模型自行解除標籤。
- 文件庫把論文標為研究文章（背景證據）與觀察性研究，也把技術 JSON 收在折疊區。

## 建議修正優先序

1. 先處理 ertapenem 的來源矛盾攔截，以及所有失敗分析列的「不可供審閱」行級標示。
2. 再把 `有支持／適合使用` 改成帶來源與未驗證狀態的中性語句，並將最終狀態前移。
3. 將 Agent 的 `需確認` 拆成模型自述、格式／來源檢核、引用適用性三類，給出具體下一步。
4. 最後精簡逐藥證據準備表與文件技術警告的顯示方式。
